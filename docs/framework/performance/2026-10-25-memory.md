# Runtime allocations: gzip, i18n, and static templ CSS

This investigation follows the root-website profile that showed repeated CSS
construction, URL/i18n work, and a new compression buffer per response. Changes
are in the framework; the consuming website dependency has not been updated.

## Measured changes

Measured on 2026-10-25 inside the existing no-js Dev Container: Go 1.26.7,
linux/arm64, GOMAXPROCS=15, pinned templ v0.3.1001. Each benchmark ran three times.
These numbers measure cumulative allocations per operation, not process RSS.

| Operation | Before | After |
| --- | --- | --- |
| Gzip response, 512-byte payload | 816096–816105 B/op, 31 allocs/op | 2490–2609 B/op, 14 allocs/op |
| Runtime PathFor, configured locale | 456 B/op, 5 allocs/op | 24 B/op, 1 alloc/op |
| Constant CSS function, two properties | 272 B/op, 7 allocs/op | 0 B/op, 0 allocs/op |

Timing for the gzip baseline varied substantially; no latency improvement is
claimed. The CSS probe compares upstream templ output with the framework wrapper
using the same source, toolchain, dependency, and benchmark. It compiles both
outputs, verifies the class ID and stylesheet content, and verifies a dynamic
property still changes at runtime.

## Implementation and ownership

- `framework/httpserver`: reuse gzip writers through sync.Pool. Close each stream
  before returning its writer; reset the destination to io.Discard so the pool
  does not retain the response writer. Keep existing encoding negotiation and
  flush behavior. A burst can retain compression buffers until GC clears the
  pool; lower allocation volume does not guarantee lower idle RSS.
- `framework/i18n`: Runtime and Resolver use their already-normalized private
  configuration. Public LocalizePath and StripLocale still normalize caller
  input. Runtime.Config returns a defensive snapshot, matching Resolver.Config,
  so callers cannot mutate the internal configuration through slices or maps.
- `internal/bundler/templgen`: replace declarations consisting only of constant
  CSS properties with a generated private CSSClass value and the original public
  or private function signature. Compute the exact templ class ID at generation
  time. Any expression property stays with upstream templ, including expressions
  that read a package variable from a parameterless function. The generated
  stylesheet and component rendering therefore keep the same IDs.

The follow-up below optimizes simple class lists. The website independently
normalizes domains once and parses links once. No global page-response cache or
replacement renderer was introduced.

## Reproduction and checks

From the framework root inside its Dev Container:

```sh
task perf:bench
task perf:css-probe
task perf:race
task test
```

`task test` includes golangci-lint, deadcode, and all Go tests. If deadcode is
missing, install it inside the container using the same command as CI:
`go install golang.org/x/tools/cmd/deadcode@latest`.

The gzip allocation budget is checked in the ordinary test suite. Race
instrumentation deliberately discards some sync.Pool entries, so perf:race
checks stream isolation and failure recovery without applying that budget.

No production change or whole-website RSS result is included here. The website
still pins an older no-js revision. Its next validation must regenerate assets
and Go code, run its Taskfile checks, and repeat the same HTTP workload with the
framework change before claiming a production memory reduction.

## Follow-up: default request-path work

The expanded investigation preserves the framework mental model: generated App
Bundle, app-owned services, templ rendering, no-js metadata/HTMX, and route-static
asset discovery. Request limits remain deployment policy; no application admission
limits or overload 503 responses were added.

Additional three-run component measurements on the same framework toolchain:

| Operation | Before | After |
| --- | --- | --- |
| Health with 500 global CSS classes | ~64361 B/op, 539 allocs/op, ~61–67 microseconds | 1096 B/op, 13 allocs/op, ~1 microsecond |
| Literal message rendering | 80 B/op, 2 allocs/op | 0 B/op, 0 allocs/op |
| Five-language alternates | 4819 B/op, 54 allocs/op, ~6.1 microseconds | 2401 B/op, 37 allocs/op, ~3.1 microseconds |
| Four-item simple class list | 456 B/op, 7 allocs/op, ~455 ns | 24 B/op, 1 alloc/op, ~33–34 ns |
| Already-compressed 32 KiB binary fixture | ~207–229 microseconds, ~61000 B/op | ~4–11 microseconds, 33792 B/op |

Health and static files now dispatch before templ CSS middleware. They no longer
build page CSS context state. Main page rendering, exact handlers, and custom
composition retain CSS handling.

Literal compiled messages return their existing text. Alternate URLs construct
one i18n Resolver rather than normalizing configuration separately for each
language.

The generated class-list conversion calls `framework/templruntime.ClassNames`.
Only strings, ConstantCSSClass, and ComponentCSSClass in lists of at most eight
items take the bounded scan path. Other inputs delegate to the pinned templ
implementation, preserving conditional disabling, nested inputs, custom/unknown
values, ordering, and deduplication. The generator rewrites only generated templ
function bodies, preserves CSS registration and HTML escaping, and selects an
import alias that cannot collide with source identifiers. User Go functions are
not transformed. This is generated-runtime support, not a second template engine.

Known compressed image/font/archive/media types no longer receive a second gzip
layer. SVG, HTML, WebAssembly, and unknown types retain existing compression.
Content-Length and identity bytes are preserved when compression is bypassed.

Reproduce the additional checks from the framework root:

```sh
task perf:hotpaths
task perf:metadata
task perf:classes
task perf:binary-assets
task perf:generator-test
task perf:race
task test
```

The website integration report is `root-website/docs/performance-memory.md`. It
includes process RSS/HWM, Docker working-set measurements, local modfile workflow,
excerpt processing and bounded per-service memoization, and limits of the result.
In the constrained one-CPU local HTTP run, sampled working set dropped to ~7.6–8.3
MiB and throughput improved from ~240 to ~343 req/s. These working-set numbers do
not establish a total-process 10 MiB guarantee: peak RSS was ~16.1 MiB, and a
separate hard Docker 10 MiB stress run was OOM-killed at concurrency 32.

Neither repository's changes were committed or deployed during this investigation.
The website must pin a real framework revision through an authorized release
workflow before publishing newly generated runtime-helper imports. Whole-server
performance also depends on the CMS dataset and deployment CPU/memory settings.

### Compatibility review

A follow-up review reproduced a generator regression for a local `templ` variable
inside a nested user function within a template. The class-list AST optimization
now checks identifier binding and leaves that user declaration untouched. A
regression test failed before the fix and passes after it. Public templ class
calls still use the optimized helper.

### Independent review: CSS receiver methods

A second review reproduced a compile regression for constant CSS methods with the
same name on different receiver types: caching by method name emitted duplicate
package variables. Static CSS precomputation now applies only to free functions;
receiver methods retain upstream templ generation. A regression test covers
generic value and pointer receivers, and the previously failing standalone
fixture compiles after the fix. No consuming-app source migration is required.
